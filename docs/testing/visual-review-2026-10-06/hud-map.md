## Strong findings

### 1. P2 — Scheduled departures can disappear from the full map until pushback

**Trigger:** book a freshly acquired player aircraft on its stand, or inspect an AI aircraft whose first departure is still scheduled. `Presentation/AirsidePrototype.Airline.cs:1667` immediately skips any aircraft without `CurrentDestination`. `Simulation/FleetAircraft.cs:196–199` separates the trip in progress from `Scheduled`; `Simulation/AirlineOperations.Runway.cs:280` sets only `Scheduled`. The simulation copies the scheduled destination into `CurrentDestination` when pushback actually starts (`Simulation/AirlineOperations.cs:1145–1148`). AI first departures likewise set only Scheduled (`AirlineOperations.AiTraffic.cs:104`).

**Consequence:** although the aircraft has a real scheduled flight and a drawn stand position, LocateMapFlights never reaches TryMiniMapLocation, so it has no icon/hit target and is omitted from the “All flights” count. It becomes selectable after pushback. This contradicts the latest GAME.md claim that scheduled departures are included. Restricting the trigger to aircraft without a previous CurrentDestination avoids assuming every returned aircraft has its previous trip cleared.

**Fix:** obtain the route destination from `CurrentDestination ?? Scheduled?.Destination` for eligible on-field flights; keep the off-map profile branches dependent on a current trip. Decide explicitly whether cancelled schedules are eligible; retain the requirement for a real location. No simulation mutation is required.

**Headless acceptance:** extract/use the actual runtime full-map eligibility/location row builder in the harness. With an AtStand aircraft whose CurrentDestination is null, a valid Scheduled destination and a supplied geographic stand location, assert the row, registration hit target, route destination and count all appear before departure. Include a first-bank AI scheduled departure, active taxi departure and inbound row; assert cancelled/unscheduled cases according to the chosen policy. A test of RegionalMiniMap.Pick alone cannot catch this upstream omission.

### 2. P2 — Explicit planning and selection transitions leave the old inspector active

**Trigger A:** inspect a player flight, then use its PLAN FLIGHT / VIEW PLAN primary action once its state makes that action available, or leave the map and explicitly open planning for a player aircraft. `RunSelectionAction` dispatches these actions to OpenPlanner (`AirsidePrototype.Airline.cs:1247–1249`). `OpenPlanner:1541–1569` changes planning identity/destination and resets the lens but never clears `_mapFlightInspectorId`.

**Trigger B:** use a hold/blocker link from the map inspector, or the next/previous selection keys while it remains open. `FollowHoldLink:1105` and `CycleSelection:1413` call SelectAircraft; `SelectAircraft:1367–1399` changes `_selectedAircraftId` but never updates/clears the inspector ID. For a player blocker, the existing planner-stays-open branch preserves the map.

**Consequence:** `DrawDestinationsMap:1732` still suppresses planning details solely because `_mapFlightInspectorId != null`. `DrawMapFlightInspector:2027` still looks up the old aircraft by that ID. An explicit plan request appears to do nothing, or the selection highlight/tracking refers to a new aircraft while the visible dossier refers to the old one. This state persists across reopening the map because closing workspaces also leaves the ID set.

**Fix:** make planning mode and flight inspection mode explicit mutually exclusive states. Clear the inspection ID when OpenPlanner explicitly enters booking. When a card selection/hold link changes the inspected target, either update the inspector target and retain map context, or exit inspection before showing the new selection. Ordinary destination selection already clears it (`PickDestination:2221`) and provides the intended precedent.

**Headless acceptance:** put the actual transition logic behind a pure state helper, or compile/test the runtime dispatcher with a minimal seam. Assert inspector A → explicit Plan B results in booking B with inspector cleared; inspector A → hold-link B never continues rendering A; close/reopen through explicit planner entry must not resurrect A. Also retain the intentional distinction in ADR 0237: clicking a flight to inspect it alone must preserve the existing planning aircraft. Existing `FlightInspectorReplacesPlanningDetailsRatherThanPaintingOverThem` only tests the painter's showDetail=false output, so it cannot detect these dispatcher/state defects.

### 3. P2 — On-field map aircraft icons use runway-relative yaw on a north-up map

**Trigger:** any on-field aircraft with a view in `_fleetViewById`. `AirsidePrototype.Airline.cs:1801–1802` assigns `fieldView.eulerAngles.y` directly to HeadingDegrees, which DrawPlaneIcon applies as a GUI rotation at `1916/1920` and `2205–2209`.

**Consequence:** geographic positions are converted correctly through YpadFrame, but heading is not. `Simulation/YpadFrame.cs:5–10` defines world +x along runway 05→23, not geographic east; `ToLatLon:49–55` rotates world coordinates into east/north. From its actual threshold constants, runway 05 has true bearing **50.18997°**. A view heading along world +x has Unity yaw **90°**, so its full-map icon points due east rather than along the runway. With the map's own longitude aspect correction (cos 27°, `AustraliaMapLens.cs:119–128`), projected runway heading is **52.33574°**, a **37.66426°** display error. A truly northbound aircraft has world yaw ~39.81003°, which is displayed northeast instead of north. This occurs at normal supported resolutions; it is unrelated to HUD scaling.

**Fix:** convert a small world-forward displacement from the actor through YpadFrame.ToLatLon, project origin and endpoint through the same map lens, and derive the icon rotation from their GUI delta. This preserves both the field-frame rotation and the map's projection aspect. Do not merely subtract a magic runway angle. Translation by the floating render origin cancels in the direction delta.

**Headless acceptance:** test the helper actually used by the full-map renderer with world +x/+z and all four runway directions; compare the icon heading with a projected geographic forward segment. Include a true-north track mapped via UnityYawFromTrue, and nonzero floating origin. Existing YpadFrame round-trip / arrival-position tests prove position conversion but do not cover this heading branch.

## WS-A / layout claims checked and rejected or qualified

- **A2 is rejected as written.** The proposed three-line string “Ready to buy · flies domestic routes…” is built as RequirementLine (`FleetWorkspace.cs:285–289`), but the market painter does not display it when CanBuy=true. At `FleetWorkspace.cs:873–875`, ready offers display CashWarning or StandLine instead. Proving that the unused requirement template wraps cannot prove visible clipping. Actual blocked requirements and cash warnings deserve separate concrete-string/font checks; the backdrop text box is indeed only 30 points high.
- **Raw 1024×640 layout is not the runtime viewport.** `AirsidePrototype.cs:1027–1031` computes ScaleFor, sets GUI.matrix and constructs the layout with Screen.width/scale and Screen.height/scale. 1024×640 gives scale 0.711111 and virtual **1440×900**. 1024×768 gives **1440×1080**; 1280×720 gives **1600×900**. The full map has a 320-point detail pane and a 717-point body height in the first case. It does not drop to the 1024-point workspace layout exercised by the direct layout tests. Claims about short/narrow fallback inspector clipping must first show a physically supported viewport whose normalized dimensions actually enter that branch. For the cited supported sizes, `Detail.IsEmpty` is false.
- **A3's effective size arithmetic is right; its claimed defect remains a policy/readability hypothesis.** 11-point text becomes ~7.82 physical pixels at 1024×640. HudPainter's Max(8, rounded FontSize) (`HudPainter.cs:243`) is a virtual-font floor, before GUI.matrix scaling. There is no established nine-physical-pixel requirement in the cited code, and raising the scale floor to .75 reduces virtual height below the layouts' intended 900-point design. A unilateral clamp increase is not a safe layout fix. Validate native readability at the supported minimum before introducing a floor; any floor must keep geometry and text sizes consistent.
- **A1 is an audit lead, not five proven clipping defects.** Absence of FitFontSize is confirmed in the named painters, but the helper is not a proof of fit and its Measure uses a deliberately conservative 0.70 em/glyph approximation (`HudShell.cs:489–493`). RouteMap uses Measure mostly for geographic label placement, and SelectionCard uses it for an identity offset; neither fact means all their dynamic text is fitted. For example, a 320-point map inspector gives SelectionCard's route line only **176 points** while Follow is enabled (`SelectionCard.cs:224–228`), and the runtime prepends operator/type to that line (`AirsidePrototype.Airline.cs:1229–1240`). This is a concrete native-font fit target, but this audit does not claim exact truncation from an approximate character metric alone. Test actual catalogue strings and supported name limits against the font/available width, then assert the chosen wrapping/ellipsis policy in headless tests.
- **Inspecting B then choosing a destination and returning to planning A is intentional.** ADR 0237 explicitly says to preserve planning identity when inspecting a flight. Do not “fix” SelectMapFlight by switching the planning aircraft on every flight click. The defect above concerns explicit planning/selection commands that retain stale inspection state.
