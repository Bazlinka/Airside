## Safe workflow structure

Use a single coordinator to own the three central status documents (GAME.md, CHANGELOG.md, visual backlog), art-manifest reconciliation, generated harness integration, native verification scheduling, and merge ordering. Each implementation branch supplies exact task packet, changed behavior, evidence and proposed status text; the coordinator includes required GAME/CHANGELOG changes in the same final behavior commit before pushing. Separate worktrees and an explicit path-ownership table are required.

- HUD owner: explicit HUD/workspace files and pure layout tests; shared painter scaling decisions belong to this owner.
- Scenery/shader owner: AdelaideGround, Surroundings, SuburbBuildings shaders and their uniform producers, suburb runtime mesh/LOD builder. Serialize H1/C1/D1 touching these files, or split with explicit handoff boundaries; one owner integrates the combined material behavior.
- Building-data owner: airport-height extraction/source data, AdelaideBuildings, audit script/generated audit and provenance. E1's existing scope is missing AdelaideBuildings.cs and the LiDAR preparation/source files required to change heights.
- Weather/performance owner: weather runtime files and extraction of pure budget helpers. Validate any shader/material interaction through the scenery owner.
- Docs owner/coordinator: optional-plan status and G1–G3, with no automatic reopening of freight priorities or historical owner acceptance.

Harness regeneration runs once on the integrated source after all relevant additions, not concurrently in the shared checkout. Native checks cover the integrated shader/runtime changes; pure checks are recorded as supplementary. Implement one accepted criterion per narrow commit. Audit/report work can run in parallel while remaining read-only, as this review did.

No additional code defects asserted: this review establishes report/workflow corrections and limitations; it does not establish new visual regressions from static source alone.
